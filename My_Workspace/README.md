# Bundu Restaurant

A comprehensive restaurant ordering and management system built with Flask and vanilla JavaScript.

## Setup Instructions

### 1. Environment Configuration

Before running the application, you need to set up your environment variables:

```powershell
Copy-Item .env.example .env
```

Staff signup requires a one-time invitation generated by a manager. Each key is bound to the invited email and account type, expires after seven days, and can be used once; generating another invitation for that email and role replaces the earlier unused key. The initial manager can be registered using `BUNDU_MANAGER_REGISTRATION_KEY` only while no active manager account exists. Generate independent random values for `BUNDU_JWT_SECRET` and this initial-manager bootstrap key (for example, with Python's `secrets.token_urlsafe(48)`). For production, set `BUNDU_ENV=production`. Managers can add staff accounts directly from the Staff roster page and generate login passwords there. Keep `.env` private and never put these values in frontend code.

```
BUNDU_ENV=development
BUNDU_JWT_SECRET=<random-secret-at-least-32-bytes>
BUNDU_MANAGER_REGISTRATION_KEY=<random-initial-manager-bootstrap-secret>
BUNDU_ALLOWED_ORIGINS=http://127.0.0.1:5500,http://localhost:5500
BUNDU_RATE_LIMIT_STORAGE_URI=memory://
BUNDU_FRONTEND_URL=http://127.0.0.1:5500
PAYSTACK_SECRET_KEY=
PAYSTACK_CURRENCY=ZAR
```

`BUNDU_ALLOWED_ORIGINS` is a comma-separated list of exact frontend origins; set it to your deployed HTTPS origin(s) in production. HTTP is accepted only for localhost during development. The in-memory rate-limit store is suitable for local development and a single process. Configure a shared store such as Redis with `BUNDU_RATE_LIMIT_STORAGE_URI` when deploying multiple workers.

### Complaint response email (SMTP)

The manager can save a complaint response without sending it, then send it from the manager page. Configure `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, and `SMTP_USE_SSL` in the root `.env`; these values are only read by the backend and must never be added to frontend code. `SMTP_FROM` is optional and defaults to the authenticated `SMTP_USER` mailbox. The root `.env` is the only runtime environment file; `.env.example` is a safe template, not another active configuration. Gmail normally uses `smtp.gmail.com`, port `587`, and `SMTP_USE_SSL=false`; use a Google App Password (with 2-Step Verification enabled), not your account password. Outlook/Microsoft 365 normally uses `smtp.office365.com`, port `587`, and `SMTP_USE_SSL=false`; the mailbox must be permitted to use authenticated SMTP by its organization. For implicit TLS on port `465`, set `SMTP_USE_SSL=true`.

Complaint delivery state is added to the existing SQLite database automatically when the backend starts. A failed delivery is recorded and can be retried from the manager page. A response that was successfully sent cannot be edited or resent through the current interface. If provider SMTP is unreliable or unavailable, a transactional email API such as Resend or SendGrid is a recommended alternative; it would require replacing the backend SMTP transport with that provider's server-side API.

### Complaint assistance

Managers can use **Generate solution** on a complaint to draft an editable customer reply. This does not require classifier training or setup. Gemini drafts use redacted complaint text and similar resolved cases; configure `GEMINI_API_KEY` in the root `.env` to enable generation. The default model is `gemini-3.5-flash-lite`; override it with `GEMINI_MODEL` if needed. If Gemini is unavailable, the manager sees the closest resolved response when one exists. The first generated draft is saved with its complaint record and has no automatic expiry; it remains until the complaint data is removed. Generated and retrieved text is never sent automatically: the manager must review and explicitly save/approve before sending.

### 2. Install Dependencies

```powershell
.\.venv\Scripts\python.exe -m pip install -r Backend\requirements.txt
```

### 3. Run the Application

```powershell
.\.venv\Scripts\python.exe Backend\app.py
```

The application loads the root `.env` file and starts with debug mode disabled on `http://127.0.0.1:5000`. For deployment, use a production WSGI server behind HTTPS rather than Flask's development server. The Render deployment serves the API and frontend from one HTTPS origin.

### Deploy to Render

The repository-root `render.yaml` provisions a Docker web service, PostgreSQL database, and persistent disk. Its Docker build creates the Vite frontend and runs the Flask API with Gunicorn. The web service and database use paid plans, and the disk adds storage cost; review Render's current prices before creating the Blueprint. The project is in `My_Workspace/`, so keep the Blueprint file path as `render.yaml` when connecting the repository.

In Render, create a new Blueprint from this GitHub repository and review the service, database, and disk costs before confirming. Enter a Paystack **test** secret key when Render prompts for `PAYSTACK_SECRET_KEY`; do not enter a live key for this test deployment. Render generates the JWT and initial manager bootstrap secrets. After the service is live, open its HTTPS URL and register the first manager using the generated `BUNDU_MANAGER_REGISTRATION_KEY`; the production PostgreSQL database starts empty, and local SQLite accounts/orders are not copied automatically. Configure the Paystack dashboard webhook to `https://<render-service-host>/api/payments/paystack/webhook` and test a checkout using Paystack test credentials. Keep all keys in Render's backend environment settings, never in the frontend or source control.

### Paystack online payments

Online orders use Paystack-hosted checkout in ZAR. The backend calculates order totals from the current menu, starts checkout with Paystack, and does not send online orders to staff until a signed Paystack webhook or server-side transaction verification confirms payment. If Paystack is not configured, online checkout is rejected and customers can still choose cash or card with their waiter.

Set these as **backend environment variables** (never in frontend code):

- `PAYSTACK_SECRET_KEY`: your Paystack test or live secret key.
- `PAYSTACK_CURRENCY=ZAR`: the current checkout flow supports South African rand.
- `BUNDU_FRONTEND_URL`: the exact frontend origin, such as `https://orders.example.com`. It must also appear in `BUNDU_ALLOWED_ORIGINS`.

In the Paystack dashboard, configure `https://<your-api-domain>/api/payments/paystack/webhook` as the webhook URL. Paystack signs webhooks using your secret key; no separate webhook secret is required. The server verifies the signature, transaction reference, amount, and currency before marking an order paid. For local testing, use a test secret key and expose the local API to Paystack with a secure tunnel, then set the dashboard webhook URL to the tunnel's `/api/payments/paystack/webhook` endpoint. The customer return page also asks the backend to verify the transaction with Paystack. Do not commit or share secret keys. Live payments require valid live keys, deployed HTTPS URLs, and a tested webhook configured in the Paystack dashboard.

Open `My_Workspace/` as the VS Code workspace. In a terminal, run `npm install` from `FrontEnd/`, then start the public site with `npm run dev` from that folder. Vite serves the React-powered home, menu, and DineDesk Kitchen at `http://127.0.0.1:5500`; start the Flask API separately as described above. Build the frontend for deployment with `npm run build` from `FrontEnd/`. The existing staff and account pages remain part of the same site.

Guests can place an order and then reserve a table for a future half-hour slot. Order-linked reservations hold a table for 60 minutes, include a separate R50 fee for the waiter to record as paid, and are checked against existing table bookings and active orders. Dine-in orders require a currently available table; the API rechecks availability inside the order transaction.

Customers verify their email by code to access past orders. The checked **Remember this device for 30 days** option keeps that browser signed in for order history; uncheck it for a session-only login, or use **Use a different email** to clear the saved access. The manager overview groups revenue by South African business date. Resetting today’s dashboard totals starts a new reporting baseline without deleting orders or exports.

Staff can open the login page from the DineDesk wordmark in the public-page header.

Waiter and manager sign-ins and sign-outs are recorded in SQLite. Managers can add chefs, waiters, and managers with individual hourly pay rates, and schedule staff for dated shifts. Waiters and managers receive sign-in accounts; chefs are roster-only. A scheduled staff member is marked absent after their shift ends if they have not signed in that day. The manager's **Shifts** section shows daily hours and monthly gross-pay estimates using each staff member's hourly rate, with overtime after 45 hours in a week at 1.5×. These are gross estimates and do not include tax or other deductions. Attendance records are retained for reports and manager-only exports. The **Exports** section downloads orders, pantry and stock movements, staff and shifts, complaints, reservations, waitlist entries, or all company records as PDF documents.

## Project Structure

- **Backend/** - Flask API server with order management, authentication, and complaints system
- **FrontEnd/** - React/Vite public home, menu, and ordering experience, with existing staff and account pages
- **.vscode/settings.json** - Prevents Live Server from serving environment files, backend files, or the virtual environment
- **.env.example** - Template for environment configuration (copy to `.env` before running)
- **.gitignore** - Excludes environment files, SQLite databases and backups, uploaded images, the virtual environment, and Python caches
